# V3.2 Beta — thermo-nuclear code-quality review

Status: review completed 2026-11-02 against the uncommitted V3.2 batch.
Method: the `thermo-nuclear-code-quality-review` skill: look for structural
regressions, boundary leaks and “code judo” moves that delete complexity rather
than move it. Host/build evidence is in `v3.2-validation.md`.

This review is intentionally stricter than “it compiles and the host tests
pass”. It records what was fixed before the beta and what is accepted debt.

## Findings fixed before release

### 1. Tagtree reached into tagcache search internals

`tagtree.c` saved and restored `tcs.position`, `tcs.entry_count` and
`tcs.ramsearch` directly. Those fields are marked “for internal use only” in
`tagcache.h`; the UI was depending on a private layout.

Fix: added `struct tagcache_search_cursor` plus
`tagcache_search_save_cursor()` / `tagcache_search_restore_cursor()`. The
restore path validates the backing store, remaining entry count and position,
so a rebuilt or shrunk tag file is rejected instead of seeking past it.
`tagtree.c` now stores only the opaque cursor.

### 2. Two cache-invalidation paths in `file.c`

The read-ahead work added a `nsectors` range to the stream cache, but the old
local `discard_cache()` only cleared `flags`; it left `sector` and `nsectors`
looking valid. After a dropped ENOSPC write, a later read could serve the
never-persisted buffer.

Fix: deleted the local helper and used the canonical
`filestr_discard_cache()` at both ENOSPC sites. One invalidation path, one
invariant: `nsectors == 0` means invalid.

### 3. Path-lookup policy leaked into the generic VFS

The generic `open_path_component()` loop is FAT-shaped: it calls `readdir`,
decodes ISO names and compares with `strcasecmp`. HFS+ needs a different
lookup policy but the old code had no hook.

Fix: added `hfsplus_find()` and routed only read-only HFS+ volumes to it from
`open_path_component()`. Non-HFS+ volumes keep the existing readdir loop, so
FAT ISO-name handling is untouched. HFS+ own a bounded positive/negative name
cache, keyed by logical/backing parent and exact name; an overlay entry sync
bumps the cache generation, so create/rename/remove/write-shadowing invalidate
all cached lookups. The readdir walk remains the canonical fallback.

### 4. `tagcache_fill_tags()` prototype hid behind `HAVE_DIRCACHE`

The implementation is now available for any `HAVE_TC_RAMCACHE` build, but the
public prototype was still dircache-only. `playback.c` and
`playlist_viewer.c` worked around it with local declarations, which is exactly
how signatures drift.

Fix: exposed the prototype under `HAVE_TC_RAMCACHE`; removed both local
declarations. Same for `albumart_cache_clear()`, now declared in
`apps/recorder/albumart.h` instead of `playback.c`.

### 5. Plugin build broke on the new filename descriptor

`close_filenametag_fd()` was defined inside the `!PLUGIN` block but called from
the plugin's `remove_files()`/`thread()` paths. The first full firmware build
failed at `tagcache.rock` with an undefined reference.

Fix: moved the definition outside the `!PLUGIN` block and kept the plugin body
mutex-free (the plugin never opens the persistent lookups). The full firmware
and plugin build now links.

## Structural findings accepted for the beta

### A. ATA tick policy is still flag-heavy

`storage_ata-6g.c` now has `ssd_wake_pending`, `ssd_wake_tick`,
`ata_force_sleep` and `ata_cache_dirty`. The tick handler computes
`auto_sleep`/`explicit_sleep`/`allow_sleep` and nests the deep-sleep and
explicit-sleep paths. An explicit `enum ata_power_state` and a single policy
function would read better, but this is a 1,500-line target driver whose resume
behavior cannot be validated on the current machine.

The Beta 1 `ata_idle_notify_tick`/`Q_STORAGE_IDLE_NOTIFY` path was removed in
Beta 2 after it caused a 4–6 s post-boot freeze on iFlash SD. Do not
reintroduce a periodic early-boot callback without a device test.

Decision: keep the conservative behavior and document the debt. Do not
refactor power state and claim safety without the 100-cycle hardware test.

### B. `tagcache_fill_tags()` has two compile-time backends

The dircache branch reads tags from the RAM index directly; the non-dircache
branch uses `tagcache_find_index()`/`tagcache_retrieve()`. Their field mapping
is similar but not shared. A table-driven accessor could remove the duplicate
`SET`/numeric block, but it would add a function-pointer or mode switch to a
hot path and make the two backing-store contracts less obvious.

Decision: retain the two explicit backends. They are selected at compile time,
not by runtime branching, and each is small enough to audit.

### C. `hfsplus_namespace.c` has two readdir walks

v3 uses the parent hash buckets; v1/v2 and repaired chains use a bounded linear
fallback. The branching is confined to `overlay_readdir_next()` and is required
by the legacy format contract, not incidental feature creep.

Decision: keep. The helper owns the policy and the phase state is explicit.

### D. File sizes

`file.c` (1,436 lines) and `tagcache.c` (5,700+ lines) were already far beyond
the 1,000-line threshold before this batch. The new logic is isolated in
helpers (`cache_contains`, `readahead_allowed`, `readahead_invalidate`,
`tagcache_search_cursor`, `hfsplus_find`, `overlay_readdir_next`). No new
mega-file was created; `hfsplus_namespace.c` remains under 650 lines.
